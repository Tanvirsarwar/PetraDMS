# PetraDMS - Decisions log

Non-obvious decisions made during the build. The plan (`docs/PetraDMS_Product_Architecture_Plan_v2.md`) stays authoritative.

## D1. Prototype `index.html` was not supplied
The plan references an `index.html` prototype for tokens, layout and demo data. It was not in the upload. Fallbacks used:
- Colours: the plan's own fallbacks (red `#C8202F`, black `#121212`, cream `#F6F1E7`).
- Demo data: the supplied `Readable_Product_SKU_List.md` (Marks, Ama, SS, tea, noodles, beverages) plus invented Bangladeshi customers.
If the prototype is added later, only `apps/desktop/src/styles/tokens.css` and the demo seed need to change.

## D2. Bundling instead of shipping node_modules
The Electron main and preload are bundled by esbuild into `dist-electron/*.cjs`; the renderer is bundled by Vite into `dist/`. The installer ships no `node_modules` and no native addons. This keeps the pnpm workspace layout from breaking electron-builder and honours "no native addon" for `node:sqlite`.

## D3. TypeScript 5.9 rather than 7.x
TypeScript 7 exists on npm at build time, but typescript-eslint and the Vite/Vitest toolchain are validated against 5.9. Pinned to 5.9.3. The plan only requires "latest stable" for Electron.

## D4. Electron 44.5.1 pinned
Latest stable at build time. It bundles a Node that provides `node:sqlite` without a flag; verified by the Playwright spike test (WAL + integrity_check inside Electron) and by the CI smoke test against the installed, packaged app.

## D5. Smoke-test flag
`PetraDMS.exe --smoke-test` opens the database in the packaged app, writes `PETRA_SMOKE_OUT`, and exits 0/1. CI uses it after a silent NSIS install. It does nothing for a normal launch.

## D6. Network blocking
Besides having no code that calls the network, the main process cancels every request that is not `file:`, `data:`, `blob:` or `devtools:` (and `localhost` in dev). The renderer CSP also restricts `connect-src` to `'self'`.

## D7. Installer artifact and release
CI builds on `windows-latest`, requires the installer to exceed 50 MB (a stub-only build would not), silently installs it, launches the installed app with `--smoke-test`, and only then uploads the artifact `PetraDMS-Windows-x64-Installer`. `release-windows.yml` does the same for `v*.*.*` tags and attaches the `.exe` to a GitHub Release with `gh release create`.

## D8. Code signing
No certificate is available. `signAndEditExecutable` stays true so icon/version metadata are applied; the installer is unsigned and Windows SmartScreen will warn (plan section 18).

## D9. Engine design (Phase 2)
- Prices on a product are per BASE unit; a pack may override its own tier prices (NULL = factor x base price). This avoids sub-poisha prices for gram-based goods.
- One generic `reverseDocument` negates every still-live stock, ledger and cash row of a document (`reverses_id` points at the original). Void, invoice edit and day reopen all use it, which is why invariant I7 holds structurally. Voiding or editing needs the document's business date to be open: after a day is closed, corrections go through returns or adjustments, so closed history never changes.
- Sale edit keeps all revisions of `sale_items` (`revision` column); only the current revision counts toward totals. Edit and void are blocked while a live return exists.
- Expiry-tracked products never allow negative stock, even if the Owner enables it for others; this keeps I2 exact.
- Negative stock (Owner setting): the uncovered part of a sale is costed at last purchase cost, and a later purchase only adds the value of units that remain.
- Purchase return: stock leaves at current average cost; `variance = cost_value - credit` is added to COGS (plan 5.4).
- Day close posts any cash difference to the cash book (`day_close` source) so the book equals the counted cash. Reopening reverses it. Only the most recent closed day can be reopened. I8 compares `created_at` with the day's `closed_at`.
- Credit limit 0 means "no limit". `warn` returns a warning, `approval` needs a manager/owner id, `block` rejects.
- Salary expense = sum of `salary_lines.net` by sheet month; stock loss = value of damage / expired / internal_use / adjust movements (not cash).
- Test runs use an in-memory database and an injected clock; the 1,000-scenario and 10,000-operation tests are in `packages/db/src/property.test.ts`.

## D10. UI shell (Phase 3)
- UI preferences (language, mode, animations, font size, contrast) are per-device and live in `localStorage` (`petra.ui.v1`); business settings stay in the database (Phase 4). Defaults: Bangla, Simple mode, Animations Full.
- The native Windows title bar and window controls are kept (plan 9.5 says standard controls stay untouched); no custom frame.
- Router is `HashRouter` because the packaged app loads `file://` pages.
- Motion uses the `motion` library only for modal, drawer and toast presence; everything else is CSS transforms and opacity. Durations come from the Animations setting (Reduced caps at 100 ms, Off is 0). Lite mode samples ~2 s of frames after launch and drops Full to Reduced when the median frame is above 24 ms, without changing the saved choice.
- Dictionaries are split by file under `i18n/locales/{bn,en}/*.json` (merged with `import.meta.glob`); the parity test requires identical files, keys and `{placeholders}`.
- When `PETRA_DATA_DIR` is set (tests, CI) Electron's `userData` moves inside it so runs never share Chromium state.
- The style guide is not in the sidebar; it is reached by URL or Ctrl+Shift+G.

## D11. IPC and application services (Phase 4)
- One IPC channel, `petra:invoke`, carries `(channel, input)`. The preload validates the input with the channel's zod schema; the main-process `Dispatcher` validates again, checks the signed-in user's role (`public` / `user` / `manager` / `owner`), refuses writes while the licence is read-only, runs the handler and returns `{ ok, data }` or `{ ok:false, error }`. Roles are therefore enforced in the main process, not only hidden in the UI.
- Channel outputs are typed (TypeScript) but not re-parsed with zod: they come from trusted main-process code and re-validating large lists would cost time on old PCs. Inputs are always validated.
- Errors cross the bridge as `{code, message, params}`; the preload throws them inside an `Error` message (`PETRA_ERR:` + JSON) because custom error classes do not survive `contextBridge`. The renderer maps `code` to a translated, plain-language message (`err.<CODE>`).
- Services live in `packages/db/src/app/` and take a `Host` interface for the few things only Electron can do (dialogs, moving the data folder). That keeps them testable with an in-memory database.
- The signed-in session is held in the main process (single-user desktop app); the renderer asks `app:status` on every start.

## D12. Authentication, recovery and licence (Phase 4)
- PIN (4 to 6 digits) or password (6+ characters), scrypt (N=16384, r=8, p=1), stored as `pin:scrypt$...` or `password:scrypt$...` so the login screen knows whether to show the keypad. Five wrong attempts lock the account for five minutes.
- Recovery code: 20 characters from an unambiguous alphabet (about 100 bits), shown once, stored only as an scrypt hash, reset by using it and a new code is issued. It resets the first active Owner only. There is no cloud reset.
- Licence file: `base64url(JSON payload).base64url(Ed25519 signature)`. The payload binds to a machine code (first 16 hex characters of sha256 over hostname, CPU model, platform and architecture). Renaming the PC or changing its CPU needs a re-issued key. Expiry is inclusive of the last day (end of day UTC).
- Trial: 30 days from the first status check. `last_seen_max` only moves forward; a clock more than 24 hours behind it means read-only until the clock is correct. Read-only blocks every `write` channel; viewing, printing, export and backup stay available.
- Tests and CI may override the public key and machine hash with environment variables only when the app is not packaged.
- The data folder can be chosen once, during setup (a pointer file `location.json` in `%LOCALAPPDATA%\PetraDMS` records it). If the chosen folder already holds a database, the app opens it instead of creating a new one.
- Staff start in Simple mode, Owner and Manager in Full mode; a later choice is remembered per user.

## D13. Catalog, inbound and stock (Phase 5)
- One contract file per area (`ipc/catalog.ts`); handlers in `packages/db/src/app/{catalog,inbound,catalogServices}.ts`. Staff-readable: products (cost fields null), stock, batches, alerts. Manager+: suppliers, purchases, supplier payments/ledger, movements, adjustments.
- Packs are bigger units of the base unit (factor >= 2); the base pack is implicit. Removing a pack that appears on a document is refused (IN_USE). `trackExpiry` cannot change once a product has stock history.
- Dealer price is optional in the editor and defaults to the wholesale price.
- A purchase without a supplier must be paid in full; with a supplier the unpaid part becomes supplier due. Stock adjustments always need a reason.
- Landing page after sign-in is the first registered page; a dashboard replaces it in Phase 8.

## D14. Sales, approvals and printing (Phase 6)
- `auth:approve` returns a one-time token (5 minutes, bound to the requesting session user). `sale:save` and `sale:edit` accept it as `approvalToken`; managers and the Owner self-approve. Staff below minimum price or over the credit limit get `APPROVAL_REQUIRED` and the POS opens the approval modal, then retries.
- Staff see only today's sales and never cost or profit. Return, void and edit need Manager or above.
- A walk-in sale (no customer) must be paid in full at the retail price.
- Printing is pure HTML from `@petra/core`; Electron renders it in a hidden window (`Host.printHtml` / `pdfHtml`). Fonts are embedded as base64 so Bangla prints offline. PDFs go to `<dataDir>/invoices/<docNo>.pdf`.
- In a packaged build only `file://` senders are trusted on the IPC channel; `http://localhost` is allowed only in development.

## D15. Money side (Phase 7)
- All money channels need Manager or above; only the Owner reopens a day or edits money accounts. Staff see only customers in People.
- Closing a day is allowed for today or earlier. A cash difference is booked to the cash book (`day_close`) so tomorrow's opening cash equals the counted cash. Reopening reverses it.
- One salary sheet per month (a void sheet can be regenerated). Employees with a balance cannot be archived. A negative employee balance means an advance the employee still holds.
- Money accounts cannot be hidden while they hold money, while default, or if they are the last cash account. Transfers between accounts are not in V1 (the plan has none).
- `/expenses` (Full mode) and `/money` (Simple mode) are one screen with tabs: Expenses, Cash book, Close day, Accounts.

## D16. Dashboard and reports (Phase 8)
- Profit definitions live in one function (`periodFigures`): net sales = invoice totals before tax minus returns, each by its own document date; COGS includes bonus goods and subtracts the cost of returned goods; purchases are stock, not an expense; salary comes from posted sheets whose month touches the range; stock loss is damage, expiry and own use. Dashboard, summary and every grouped report use it, and the tests tie them together.
- By-product sales add a "Rounding" row so the total equals net sales when round-off is on.
- Report results are plain tables (`columns`, `rows`, `totals`). Cells starting with `@` and `key` columns carry i18n keys, so the renderer, PDF, CSV and Excel all translate the same result. Exports use the headings the user sees; PDFs use the business print language for digits.
- Staff reports: summary, sales, due aging, collection sheet, low stock, expiring, customer statement. They never include cost, profit or stock value and are limited to today. Dashboard is Owner and Manager only; staff land on Sell.
- Excel files are written by a small built-in ZIP/XLSX writer (no network, no extra dependency); text cells that start with `= + - @` are prefixed so a spreadsheet never runs them as formulas.
- Salary in a one-day summary is the whole month's sheet (by month, as in the plan).

## D17. Search, shortcuts and compact mode (Phase 9)
- Search is a small in-memory index built in the main process (`SearchIndex`), not SQLite FTS: exact, prefix, one or two typos by word length, and a trigram pass for text inside a word. Bangla digits are folded to ASCII. The `Dispatcher` counts successful writes (`writeGen`) and the next query after a write rebuilds the index (about 0.5 s at 11,000 records, only after a change). Staff searches only products and customers; sales, purchases and suppliers are Manager and above.
- Barcodes: a burst of four or more characters under 40 ms apart ending in Enter is a scan. After the second fast character the rest is held back from the page, and if no Enter follows it is typed in after all, so slow typing is never lost. Labels use Code 128 (any SKU or barcode text works; EAN-13 would reject codes with a bad check digit).
- The calculator takes its own keys (the scan detector ignores it). Percent is "percent of the amount so far" after + or -, as on a pocket calculator.
- Compact mode is a 360 x 520 always-on-top panel in the bottom-right of the current display with an eased 240 ms resize; leaving restores the exact previous bounds and maximised state. It shows today's sales, collected, invoice count and (Manager and Owner only) cash.
- Found while testing: an empty or very long quantity made invoice arithmetic throw and blanked the window (POS totals now skip lines with no valid quantity, which also blocks saving). Quantity is now at most 9 digits, money at most ten billion taka, and every screen sits inside an error boundary that shows a plain message and a retry button.

## D18. Backup, restore and recovery (Phase 10)
- A backup is one file, `PetraDMS-<local time>-<kind>.petrabak`: a ZIP holding `manifest.json` (app and schema version, time, kind, business name, counts, SHA-256 and size of the database) and `petra.db`. The database is stored, not compressed (speed on old PCs); the manifest is read without loading the file. The file appears under its final name only when complete (written as `.part`, flushed, renamed).
- Restore never touches live data until the file has been read, its checksum matched, its schema checked (a newer one is refused) and `integrity_check` passed on the extracted copy. Then a `pre-restore` safety backup of the live data is made, the database is swapped while no connection is open, migrations run if the backup is older, and the session ends. The Owner must type RESTORE.
- Retention keeps the newest backup of each of the last 14 days, the 8 weeks before that and the last 12 months, plus the six newest routine backups (so a working day keeps its intraday copies), plus the five newest safety copies (`pre-migrate`, `pre-restore`). The newest routine backup is never removed.
- Automatic backups use the dispatcher's write counter: nothing is backed up unless data changed. They run on a one-minute tick (interval 5 to 1440 minutes, default 30), and once more on `before-quit` and `window-all-closed` (Electron emits only one of them depending on how the app ends). A failed second-folder copy is a warning; a failed main backup is logged and retried.
- The second folder is remembered in `backup-dirs.json` beside the data folder as well as in settings, because start-up recovery has to find it when the database itself cannot be read.
- Start-up recovery (before anything opens the file): if `integrity_check` fails, the newest backup that verifies is restored, the damaged file is kept as `petra.db.corrupt-<time>`, the app logs it and shows a banner until the Owner dismisses it. With no usable backup the app stops with a plain message and leaves the file unchanged. A database from a newer app version is refused the same way.
- A migration on a database that already holds data first makes a `pre-migrate` backup through the same code; if that backup fails the migration does not run. `packages/db/fixtures/petra-v1.db` is the schema-1 database, committed and never regenerated, so every later migration is tested against what an early customer has.
- The diagnostics ZIP holds versions, health, row counts, settings, the app log and the shape of the audit log. It never contains customers, products, prices, users or secrets; a test searches the ZIP for seeded names and password hashes.
- Backup, restore, audit and diagnostics channels are Owner only and are not "write" channels for the licence guard, so they keep working when the licence is read-only.
- Found while testing: `pnpm -s typecheck` hid errors from the recursive run; the gate now reads the unsilenced output.

## D19. Onboarding: import, export, demo, tour, help (Phase 11)
- Import reads a CSV the user picks (UTF-8, comma, semicolon or tab; a byte-order mark is fine; at most 4 MB and 20,000 rows). Columns are matched to fields by heading (English and Bangla aliases) and the user can change any match. Every row is checked against field rules and then against the shop (SKU, barcode and phone already used, duplicates inside the file, customers or suppliers not found); each problem has a code that is translated for the screen and for the rejects file.
- The dry run executes the real import inside a transaction and rolls it back, so it reports exactly what the real run would do, including conflicts only the database can see. The real run puts each row in its own savepoint: a bad row is skipped, nothing is half-imported, and the result says how many were skipped.
- Opening stock is entered as an `opening` stock adjustment with the cost per unit given (never for products that expire: those must be bought in so batch and expiry exist). Opening dues are ordinary `opening` ledger entries, matched by phone and then exact name.
- Money in a CSV is taka with at most two decimals (commas, the sign and Bangla digits are accepted) and becomes whole poisha; a text cell that starts with `= + - @` is written back inert in the rejects file.
- Export everything makes one ZIP: `spreadsheets/` (taka, joined names), `raw/` (every table as stored, poisha) and `database/` (a full `.petrabak`). Users are exported without PIN hashes; the licence and the app log are left out. It is a read-only channel, so it works when the licence has expired.
- Demo mode is only allowed in an empty shop. It first makes a `pre-restore` backup of that empty shop and remembers it; clearing demo data restores it through the normal restore path (typed word DEMO, session ends). This reuses the tested restore code instead of deleting rows from append-only ledgers. The deterministic sample set comes from `docs/Readable_Product_SKU_List.md` (names and SKUs; prices are sample values). A banner shows on every screen while demo mode is on.
- The tour is offered once per person (a banner, remembered in local storage) and can be started again from Help; it never changes data. The manuals are the files in `docs/`, bundled into the app, with tests that both languages have the same sections and shortcuts.
- Import, export and demo live on one screen (`/data`), reached from Settings and the Import buttons on Products and Customers, so the sidebar keeps the twelve entries of the plan.
- Found while testing: a key pressed in the same instant another keydown handler caused a re-render was lost by the tour, because its listener was re-added on every render; it now reads current values through refs.

## D20. Hardening, packaging and release (Phase 12)
- Performance is asserted, not hoped for. `packages/db/src/perf.test.ts` builds the plan's dataset in a real WAL file with `synchronous=FULL` (10,000 products, 5,000 customers, 6,000 sales) and checks the 95th percentile: search under 50 ms, save sale under 150 ms. It then adds one million synthetic stock movements with a recursive-CTE insert (`bulkMovements`) and runs every report and the product list, each under 2 s. Measured on the build machine, the slowest report took under 100 ms and the product list 330 ms with the million rows. `pnpm seed:perf` makes the same shop as a real data folder to open in the app.
- Cold start and memory are measured in the real app (`e2e/quality.spec.ts`): window ready in about 1 s (limit 4 s). Memory is the sum of proportional set size (PSS) over the Electron processes, about 285 MB (limit 350 MB). Summed resident size reads about 500 MB because every process counts the shared Electron libraries again; PSS counts each page once, which is what the machine really spends. On Windows the working set is used.
- The same file has the route sweep (every screen, English and Bangla, 1366x768, demo data: no console error, no horizontal overflow, no raw key, no `undefined`/`NaN`/`TODO`) and the keyboard-only pass (a whole sale from F4 to Ctrl+S, F2 for the next sale, every sidebar item reachable and showing a focus ring). The keyboard pass found that the "New sale (F2)" button advertised a key that did nothing on the done screen; F2 now works.
- `apps/desktop/src/i18n/copy.test.ts` is the error-copy review as a test: every error code has English and Bangla text written as a sentence, none mentions SQL, exceptions, `undefined` or `null`, and no screen text contains placeholder words or accountant jargon such as "debit".
- `pnpm verify:release` (`tools/verify-release.ts`) runs the whole gate, builds the package (`dist:win` on Windows, `dist:dir` elsewhere) and then tests the packaged app: contents, fresh start (`--smoke-test`), the committed v1 database with row counts compared to its JSON, no network request (Playwright launches the packaged executable; `fetch` and XHR to the internet must fail), and on Windows the silent install, install-over-the-top, uninstall with the data folder surviving. CI runs the package part as `pnpm verify:package`, because the Linux job has already run the rest.
- The installer is not code-signed (no certificate is available to this project). `forceCodeSigning` is false and `CSC_IDENTITY_AUTO_DISCOVERY` is false in CI so a stray certificate on a runner is never picked up. Signing is added later with the secrets `CSC_LINK` and `CSC_KEY_PASSWORD`; the README says how. Until then SmartScreen warns on first run.
- The installer is per-user and asks for no administrator rights (`requestedExecutionLevel: asInvoker`, `perMachine: false`), because many shop owners do not have an admin account on their PC. Only the English Electron locale is shipped (the app has its own Bangla and English text), which trims the installer.
- Release flow: CI builds on every push and keeps the artifact `PetraDMS-Windows-x64-Installer` for 30 days. The release workflow runs on a `vX.Y.Z` tag, refuses a tag that differs from `apps/desktop/package.json`, repeats the tests, builds and verifies, and publishes the installer with `SHA256SUMS.txt`.
- Petra Break is a canvas breakout reached from Help, About. Scores are the ten best in `game_scores` on the shop's own database; a score of zero is not stored. It uses no network and no library, and is not part of the sidebar.

## D21. Production Windows release (post Phase 12)
- **Why CI failed on GitHub and not locally.** Found by running the suite on the runner with Playwright protocol logging (the runner's logs cannot be downloaded from the build sandbox, so the diagnostic workflow posted the log tail as annotations, which can). After any action that saves a file the app called `shell.showItemInFolder`; on headless Linux that starts `xdg-open`, whose child process kept the app from exiting, so `electronApplication.close()` hung to the test timeout and the worker teardown timed out. `reveal` is now skipped when `PETRA_NO_REVEAL=1` (the e2e launcher sets it) and can never fail a save. Two real test races were also fixed (an audit-log row count read before the rows loaded; a focus-ring check that called `focus()`, whose `:focus-visible` result is browser-heuristic, now replaced by real Tab presses). No test was removed or weakened. Failed tests no longer leave an Electron process running (the next launch reaps it), CI uses 90 s tests and 10 s assertions (a runner is about three times slower) and one retry that the report marks as flaky.
- **The suite also runs on Windows** (`Checks / End-to-end tests (Windows)`), because Windows is the product. It found one real difference: summed working set counts shared pages in every process, so the memory limit (350 MB) is measured as proportional set size on Linux and private bytes on Windows.
- **Licence file extension.** The customer licence is `*.petra`. There is no `.pme` format; the `.pem` file that was handed over earlier is the vendor private key. `docs/LICENSING.md` explains both, the payload, validation, storage, renewal, revocation, expiry and key custody.
- **Machine binding uses the Windows MachineGuid** when it can be read (`reg query HKLM\SOFTWARE\Microsoft\Cryptography`), so renaming the PC or changing its CPU does not turn a paying customer read-only. Without a machine id the old host-name-and-CPU fingerprint is used, so no existing code changes. A packaged app ignores `PETRA_MACHINE_HASH`; only development builds honour it.
- **Secrets.** `packages/db/src/secrets.test.ts` fails CI if a key, certificate or token is tracked. The private licence key is not needed by any workflow and must not be added to GitHub. Code signing is optional and secret-driven (`WINDOWS_CSC_LINK`, `WINDOWS_CSC_PASSWORD`); with them the job signs and then requires a valid signature, without them it builds an unsigned installer and records that in `VERSION.txt`. No signing is pretended.
- **Installer.** `PetraDMS-Setup-<version>.exe`, per-user, no administrator rights, icon, Start Menu and Desktop shortcuts, publisher Petra, copyright and version in the executable's metadata, `runAfterFinish`. Business data lives in `%LOCALAPPDATA%\PetraDMS` (or the owner's chosen folder), never in the program folder; the uninstaller keeps it and tells a person doing a manual uninstall where it stayed (`build/installer.nsh`; silent uninstalls and upgrades show nothing).
- **Pipeline shape.** `checks.yml` and `windows-build.yml` are reusable workflows used by both `CI` (every push and pull request) and `Windows Release` (manual or version tag), so an installer is built from exactly the code that passed exactly the same checks. The artifact is `PetraDMS-Windows-x64` (installer, `SHA256SUMS.txt`, `VERSION.txt`, `RELEASE-NOTES.md`). A tag must equal `apps/desktop/package.json` and have a `CHANGELOG.md` section. If the Windows build fails, its log tail is posted as annotations.
- **Packaged-app verification** (`pnpm verify:package`) now also covers: first run in the default data folder with no environment variables, nothing written into the install folder, data surviving a restart, an upgrade from version A to a freshly built version B with every record, setting and licence state kept, and on Windows the executable metadata, shortcuts, per-user uninstall entry, signature state and a silent uninstall that keeps the data.

## D22. Version 1.1.0: company products, bulk purchase entry, box + pcs, branding and fonts
- **Rounding rule.** A purchase line of `boxes` boxes and `pcs` loose pieces at `cost` poisha per box is worth `boxes * cost + round_half_up(cost * pcs / factor)`. The pieces part is rounded once per line, never per piece, and the line amount is the authoritative figure: the posted base cost is derived from it, not the other way round. Sale lines keep their own two prices (box price and piece price), so no division happens at the counter.
- **Storage.** `purchase_items` keeps the pack the line was entered in (`qty` boxes) plus `loose_qty` base units, so the invoice prints exactly as typed. A pieces-only line is stored on the base pack (`qty` = pieces, cost per piece rounded). Free goods are their own lines (`line_kind = 'free'`, amount 0) so they add stock at no cost and never hide inside a discount. Migration `0002_company_box_pcs.sql` adds `supplier_products`, `purchase_drafts`, product default sale/purchase packs, the company invoice fields (invoice date, pay-by date, discount kind, tax, freight, duplicate reason), the line fields and `business_profile.logo`. It runs through the migrator, after the automatic pre-migration backup; the committed v1 fixture upgrades with every figure unchanged (`migrate.fixture.test.ts`).
- **Charge allocation.** A bill discount, VAT and freight are spread over the paid lines in proportion to their amounts with a largest-remainder split (`allocateByWeight`), so the parts are never negative and always add up to the whole to the poisha. Stock value of a line = amount − its discount share + its charge share. Integrity I5 now includes tax, freight and the per-line charge; new I11 checks `base_qty = qty * factor + loose_qty`, that free lines are worth zero and that posted stock matches; new I12 checks that a company link's and a product's default packs belong to that product.
- **Duplicate company invoices.** The same company invoice number from the same company is refused with `DUPLICATE_INVOICE` unless a reason is given; the reason is stored on the purchase.
- **Price suggestions** after a purchase use the paid lines only (free goods would make the cost look lower than it is) and show the margin; nothing changes until the user picks which prices to apply.
- **Company links.** A product bought from a company is linked to it automatically, with the last cost and pack remembered, so the next invoice opens pre-filled. The CSV column alias "company" now means the supplying company, not the brand.
- **Voiding a purchase** that already has live returns is refused (`HAS_RETURNS`); the returns must be voided first, so stock and dues can never be reversed twice.
- **POS box + pcs** is one cart line in the UI and two engine lines (the box part and the piece part), so the posting engine, costing and every report stay unchanged. A percentage discount applies to both parts; a fixed discount goes on the box part. Printed invoices and returns join the two lines back into "2 Box + 5 pcs". `2b5` in the quantity box means 2 boxes and 5 pieces.
- **Branding.** The trader's business name is the brand at the top of every screen and printout; "Powered by Petra DMS" and the version sit at the bottom. Vendor details live in one file, `packages/core/src/vendor.ts`; its support phone, e-mail and website are empty and must be filled before they are shown. The logo is stored in the database (a data URL of at most 256 KB, PNG/JPEG/WebP checked by its first bytes), so it travels with backups and needs no file path.
- **Fonts.** Plus Jakarta Sans (UI), Hind Siliguri (Bangla UI), Fraunces and Noto Serif Bengali (display), JetBrains Mono (numbers) are bundled from `@fontsource` and served locally; the CSP stays strict and nothing is fetched. Tokens `--font-ui`, `--font-display`, `--font-num`. PDFs embed the same faces, and Bangla text keeps a taller line height so conjuncts are not clipped.
- **Test pacing.** The app treats keys under 40 ms apart as a barcode scanner and holds them back; end-to-end tests that type into the grid therefore type at a person's pace (70 ms).

## D25. Bulk product archive and delete: history means archive, never delete

- **What.** The Products page can archive, restore or permanently delete many products at once (`catalog:productsArchive`, `catalog:productsDeletePreview`, `catalog:productsDelete`, in `packages/db/src/productsBulk.ts`). Each call is one transaction, so a failure leaves nothing half done, and writes one audit entry holding the ids and counts. A delete entry also keeps the SKU and name of what was removed, because the rows are gone.
- **Why a product with history can only be archived.** Sales, purchases, returns, stock movements, batches and adjustments all point at a product, and invoices, ledgers, the stock value and every report are rebuilt from them. Removing the product would orphan those rows or change old totals, and the integrity checks (I1 to I12) would fail. Archiving hides the product from selling and keeps everything resolving. So the delete action never hard deletes such a product: the preview lists it as blocked (with the first applicable reason: sales, purchases, stock, other history) and the delete archives it instead, counted in `archivedInstead`.
- **What counts as history.** Any row in a table with a foreign key to `products`, other than the product's own children (`product_packs`, `product_barcodes`, `supplier_products`). The tables are read from the schema at run time, so a table added by a future migration blocks deletion by default instead of being forgotten. Stock on hand or a non-zero stock value also blocks, and opening stock is a stock movement, so it counts. A product that was only imported or typed in, with no stock, can be deleted.
- **What a delete removes.** The product, its packs, barcodes and company links. The default-unit links between the product and its packs are released first, since they point at each other. The SKU and barcodes are free afterwards, so the same SKU can be imported again; archiving keeps them reserved, as before.
- **Archive rules.** `archiveProduct` has no refusal rule today (it does not look at stock), so the bulk archive applies none either. Unknown ids, repeated ids and products already in the target state are counted in `skipped` (`changed + skipped` always equals the number of ids sent), and never fail the batch. If a refusal rule is ever added to `archiveProduct`, it must be applied in `archiveProducts` too.
- **Limits.** 1 to 2,000 ids per call. A bigger selection is not split, because that would give up all-or-nothing; the screen asks the user to select fewer. Only Manager and Owner may call the channels, and the typed word is checked by the server as well as the screen.
- **Not changed.** No migration, no licensing, posting, stock or POS code, and the single-product archive button and channel behave exactly as before.

## D28. One money event, one posting: request ids and one-reversal indexes

- **Finding (Stage 1 audit of posting).** `postExpense` and `postPayment` (customer receipt, supplier payment, employee salary or advance) had no protection against being called twice with the same intent, so a double click, a double Enter or a retry after a slow answer created two documents and two cash rows. Voids were already safe: `voidExpense` and `voidPayment` refuse a document that is already void inside the transaction, and `reverseDocument` only reverses rows that have no reversal yet.
- **What changed.** The three channels (`exp:save`, `payment:save`, `emp:pay`) accept an optional `requestId` (8 to 64 characters). `postOnce` in `idempotency.ts` stores it with the first result in the table `idempotency_keys`, in the same transaction as the posting. The same id again returns that result and posts nothing; the same id with different data, or used for another kind of event, is refused with `INVALID_INPUT`. A failed attempt rolls the id back with everything else, so a corrected retry works. Ids older than 30 days are deleted when a new one is stored.
- **Opt in, on purpose.** Without a `requestId` behaviour is unchanged, because two identical expenses can be two real expenses (two teas on one day). The screens send an id created when the form opens (`ui/requestId.ts`) and make a new one after each success or cancel.
- **Voided then retried.** A retry with the id of a voided document returns the original document; it does not re-post. The void stays final.
- **Reversals.** Migration 0003 adds unique partial indexes on `reverses_id` for `stock_movements`, `party_ledger` and `cash_transactions`, so the database itself refuses a second reversal of a row. Existing data already satisfies this (invariant I7), and the upgrade makes the automatic pre-migration backup first.
- **No second record.** Nothing here adds an expense or payment table. Later DSR stages must read the existing `expenses`, `payments` and `cash_transactions` rows, not post their own.
- **Not covered in Stage 1.** Sale and purchase saving (they have their own draft and undo flow) and salary-sheet generation (which already refuses a month that exists).

## D29. DSR funds are a classification of cash rows, not a second ledger

- **Choice.** A fund is a label (`cash_transactions.fund_id`, null for ordinary business money). It never holds a balance. A fund's balance, in later stages, is the sum of the cash rows that carry its id. Alternatives rejected: a separate DSR money account (it would need transfers just to pay one expense, and a DSR expense would be two postings) and a `fund_id` copied onto expenses and payments as well (two places that can disagree). The one authority is the cash row, which is also what the account balance, the cash book and day closing already read.
- **Why it cannot double count.** Nothing is posted for a fund. An expense paid from a fund is the same one `expenses` row and the same one cash row as any other expense; the cash row has one extra column filled in. A DSR statement, the cash book and the general reports are different readings of the same rows.
- **Fixed once posted.** A trigger refuses any change of `fund_id` on an existing row (moving a row would silently change two fund balances with no posting). A correction is a void and a new entry, like any other correction. Reversals take the fund of the original in `postCash`, so a void nets to zero inside the fund (invariant I13).
- **What may carry a fund.** `postCash` accepts a fund only for the kinds listed in `FUND_SOURCES`, now just `expense`. Sales, purchases, customer payments, opening balances and day closes are business money and are refused. Later stages add their own kinds there.
- **Hidden funds.** A hidden fund takes no new postings; old ones stay, and can still be voided.
- **Roles.** Managers can read funds (they enter expenses); only the Owner creates, renames or hides them, like money accounts. The fund code is fixed after creation.
- **Compatibility.** No existing row changes and no balance is touched. A fund starts with no money: opening balances are not invented, and nothing is posted when a fund is created.
- **Known limit for Stage 3 and 5.** `cash_transactions.source` has a CHECK list, and SQLite cannot alter a CHECK in place. A new kind of movement (a DSR receipt, a transfer) needs that table to be rebuilt in a migration, or must reuse an existing kind. This is decided in those stages.
